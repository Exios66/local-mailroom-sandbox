The default path is one Modal app, `sandbox-vllm`, that starts `vllm serve` as a subprocess on port 8000 inside `vllm/vllm-openai:v0.29.0` and exposes it with `@modal.web_server`. ## What per-document and per-container metrics does a run already store?

### Takeaway
Each item can store `latency_ms`, `ttft_ms` when the caller measured it, and `prompt_tokens`, `completion_tokens`, and `llm_calls`. GPU dollars are derived from container-seconds times the repo rate table, using a telemetry window when one was scraped. vLLM `/metrics` keeps a short allow-list (TTFT mean, prefix-cache hit rate, preemptions, KV percent, length finishes, running and waiting requests) plus the raw scrape text if the caller saves it. nvidia-smi samples on the serving container are optional and on by default.

### Cited Findings
- `merge_item_metrics` writes `latency_ms`, optional `ttft_ms`, and from usage `prompt_tokens`, `completion_tokens`, and `llm_calls` into the item metrics block for `items.jsonl`. TTFT is stored only when the caller passes `ttft_ms`. The metrics module says TTFT is never inferred. — [src/mailroom_sandbox/job/usage_capture.py](src/mailroom_sandbox/job/usage_capture.py); [src/mailroom_sandbox/job/metrics.py](src/mailroom_sandbox/job/metrics.py)
- Per-agent usage, when the vendored pipeline exposes it, stores calls, prompt tokens, completion tokens, and model ids. A capture failure leaves the item without `usage_by_agent` and does not fail the document. — [src/mailroom_sandbox/job/usage_capture.py](src/mailroom_sandbox/job/usage_capture.py)
- Token USD uses `config/api_prices.yaml`, else `SANDBOX_MODEL_PRICES` in `metrics.py`. A tier applies to a whole call whose prompt reaches `min_prompt_tokens`. Qwen 3.7 Flash in that table is $0.03/$0.13 per 1M below 32k prompt tokens, $0.10/$0.40 from 32k, and $0.20/$0.80 from 256k. Decisions Luna is input-only $0.10/1M in the same table. These are repo prices, and they were not re-checked against OpenRouter on 2026-11-20. — [src/mailroom_sandbox/job/metrics.py](src/mailroom_sandbox/job/metrics.py)
- Modal GPU USD is `gpu_seconds / 3600 * rate * replicas`. `gpu_seconds <= 0` or missing yields no dollar figure. The derivation doc says: if `MODAL_BILLED_GPU_SECONDS` is absent, the serving block stays absent, and a zero is not invented. Routed runs price every distinct `modal-vllm` app in the lock for the same billed window (`gpus × rate`), which the doc calls a capacity estimate because a route that scales to zero bills less. — [src/mailroom_sandbox/job/metrics.py](src/mailroom_sandbox/job/metrics.py); [docs/RUN-COST-DERIVATION.md](docs/RUN-COST-DERIVATION.md)
- Two wall clocks disagree. Item `ts` span (`infer_wall_seconds_from_items`) starts at the first completion, so it drops the first wave. On a 5-document merger probe the doc records 100.3 seconds against a 438 second telemetry window (4.4×). At n=50 the same defect is described as about 1/waves (8–15%). The billed formula the doc prefers is `container_telemetry_after.json` end minus start, else wall plus cold boot, times replicas times hourly rate. `modal billing` output is a workspace credit cross-check, and the doc says it is not the per-run source. — [docs/RUN-COST-DERIVATION.md](docs/RUN-COST-DERIVATION.md)
- Cell cost when `min_containers=1`: `(teardown_ts - deploy_ts) × replicas × rate`. `fleet_window.json` is written by the cell runner or recovered from the telemetry volume. One file per container, named by vLLM `process_start_time_seconds`. An unrecorded window sets `measured: false` and a reason. — [docs/RUN-COST-DERIVATION.md](docs/RUN-COST-DERIVATION.md)
- In-container GPU samples (`MODAL_VLLM_TELEMETRY` default on): nvidia-smi every 5 seconds, volume commit every 2 samples, volume `sandbox-vllm-telemetry`. Fields: index, name, utilization.gpu, memory.used, memory.total, temperature.gpu, power.draw, utilization.memory, power.limit, clocks.sm. The filename key is `process_start_time_seconds` from a localhost `/metrics` scrape, because `socket.gethostname()` is the string `modal` in every container. ## What does a remote job worker miss when hotfix or vendor provenance does not match?

### Takeaway
At execution, `run_job` calls `verify_locked` and `verify_locked_hotfixes`. A lock that records `dependency_sources`, `vendor_hotfixes`, or `scoring_hotfixes` is refused when the worker image's identities differ, or when a locked hotfix is not actually in effect. Locks that predate those fields skip the check. The worker does not compare the live vLLM process with the run's engine block, and a successful `modal deploy` of the worker does not prove the image matches the lock until a run starts.

### Cited Findings
- `verify_locked` returns immediately when `dependency_sources` is missing, with the comment that historical locks predate the field. When the field is present, `describe()` must equal the frozen dojo and pipeline identities (`source`, `version`, `commit`, `tree_sha256`, and for cached snapshots `artifact_sha256`). A mismatch raises `SnapshotError`: "Dependency source drift: {dojo and/or pipeline}; restore the locked source/explicit snapshot before resuming; run locks are not rewritten". Cached snapshots are re-read from `snapshot.lock.json` during `describe()`. — [src/mailroom_sandbox/dependency_sources.py](src/mailroom_sandbox/dependency_sources.py)
- `verify_locked_hotfixes` skips a key that is absent from the lock. When the key is present, the worker's `describe()` must equal the lock, and the hotfix check must return `ok`. Mismatch raises `RuntimeError`: "this process carries hotfix code other than the locked set (redeploy the job worker from the locking checkout, or re-lock with --force)". A hotfix that is locked but not in effect raises "a locked hotfix is not in effect here" plus the check detail. The comment says activation only logs a pipeline hotfix it could not apply, and a scoring fix that is not current can drop out of the headline, which is why execution checks both. — [src/mailroom_sandbox/job/runner.py](src/mailroom_sandbox/job/runner.py)
- A started checkpoint (items already written, or cursor not at the prepared start) cannot resume if `vendor_hotfixes` or `scoring_hotfixes` is missing from the lock. The error says execution or scoring bases could mix, and tells the operator to archive and re-lock. A lock that never started, and that lacks the keys, is not refused by this branch. — [src/mailroom_sandbox/job/runner.py](src/mailroom_sandbox/job/runner.py)
- The worker image bundles the tracked vendor trees and, only when the deploying process has selected a cached or installed dojo or pipeline source, that snapshot or installed distribution plus its metadata. Default deployments carry the tracked vendor trees. `bundle_job_snapshots` does not pip-install a new revision and does not download. Installed distributions with credential-bearing `direct_url.json` are refused at image build. A snapshot whose tree hash changed between selection and bundling raises `SnapshotError` before the image is returned. — [deploy/modal_job.py](deploy/modal_job.py); [src/mailroom_sandbox/dependency_sources.py](src/mailroom_sandbox/dependency_sources.py)
- The subclass-corrections file is added because SHF-013 fingerprints it. The image comment says that without the file the worker's scoring-hotfix set would differ from the lock and the run would refuse to start. — [deploy/modal_job.py](deploy/modal_job.py)
- The image forces `DEFAULT_PROVIDER=vllm` so a bare deploy env cannot leave LegalBench on Ollama. The comment says a locked run's profile wins at activation, including an OpenRouter-engine slice. `OPENROUTER_API_KEY`, `VLLM_BASE_URL`, `VLLM_API_KEY`, Langfuse variables, and `HF_TOKEN` are copied into the deploy secret only when they are set in the deploying shell. The README says they must be exported before `modal deploy`. `run_job` drops the OpenRouter key for runs that do not call OpenRouter. — [deploy/modal_job.py](deploy/modal_job.py); [deploy/README.md](deploy/README.md)
- Dataset bytes are the volume copy. The worker verifies sha256 against the lock and does not float an HF revision. A path or generation mismatch raises before execution. — [deploy/modal_job.py](deploy/modal_job.py)
- Campaign runbook text: required unavailable or stale pipeline or scoring fixes fail readiness, and a deployed job worker must carry the lock's exact hotfix and source identities. — [config/runbooks/catalog.yaml](config/runbooks/catalog.yaml)

### Inferences
- A worker built from an older checkout will deploy cleanly and then refuse the run at `verify_locked` or `verify_locked_hotfixes` if the lock has the new fields. The failure is a `RuntimeError` or `SnapshotError` at start, after the image exists. It is not a deploy-time diff against the lock.
- A lock written before those fields will run on whatever vendor tree and hotfixes were baked into the image. The provenance check does not invent a refusal for that older shape, except when resuming a checkpoint that has already started and lacks the hotfix keys.
- The worker can be provenance-correct and still call a bad `sandbox-vllm`. Nothing in `verify_locked` reads the serving process's model id, `max_model_len`, quantization, or image tag. Those knobs are deployed separately, through `MODAL_VLLM_*` at `modal deploy` of `modal_vllm.py`. The 2026-09 sorter incident (profile default model against an AWQ fleet, HTTP 404, $0.083) is the recorded version of that split.

### Gaps
- The exact hotfix ids and fingerprints in the current tree were not re-listed here. A parallel note covers hotfixes. This note only records the refusal behavior.
- Whether a mismatch is persisted as `failed` in `sandbox-job-state` with `traceback_tail`, or dies before that write, was not traced past the `RuntimeError` in `runner.py`. The job module says execution exceptions become a persisted failed result when the generation still matches.
- No test output from this checkout was run. The refusal strings are from source, and they were not executed against a worker on 2026-11-20.

## Where can the pipeline not tell a good deploy from a bad one?

### Takeaway
Deploy success, `/health` 200, and `modal app list` state `deployed` all stop short of the checks a document-intelligence run needs: model id, context cap, quantization, kernel fallback, KV headroom, prefix-cache behavior, and replica balance. The metrics that would show a bad serving posture are optional scrapes, and several of them are defined to miss the failure (drained queue gauges, length-finish rows without tokens, a fleet-window dollar figure that the 2026-09-28 notes say under-counts the invoice).

### Cited Findings
- `/health` and `/metrics` are unauthenticated. A 200 on `/health` means the process is up. The bearer check is `/v1/models`. The `--check` smoke test prints model ids from that payload and does not send a completion, a long prompt, or a structured-output request. — [deploy/README.md](deploy/README.md); [deploy/modal_vllm.py](deploy/modal_vllm.py)
- CP-18 says the Modal 1.6.4 pin and its tests are not a live deployment claim. The Qwen3.5-9B row says `/health` and VRAM peak verification have not been done. The 2026-09-16 live parity pilot was `Qwen/Qwen3-8B`. — [docs/campaign-preparation-regressions.md](docs/campaign-preparation-regressions.md); [config/models.yaml](config/models.yaml); [deploy/README.md](deploy/README.md)
- A named image never rebuilds on deploy. A deploy can succeed on a stale published image. A rolling redeploy keeps the old model warm through the scaledown window, so a client can still hit the previous weights after a "successful" deploy. — [deploy/README.md](deploy/README.md)
- `serve()` prints a masked config and then waits for the port. It does not assert that the loaded model id, context, or quantization match a run spec. Run YAML `engine.vllm` values become `MODAL_VLLM_*` only when something exports them before deploy. The README's failure row is: change a knob, redeploy, see no effect, because the secret still holds the old value. — [deploy/modal_vllm.py](deploy/modal_vllm.py); [deploy/README.md](deploy/README.md)
- Queue depth, the 2026-09-28 signal that 97 of 100 requests stuck to one replica, is a live gauge. Before/after scrapes read 0. Prefix-cache hit rate and TTFT mean exist only after a scrape. Item `ttft_ms` is omitted when the client did not record it. — [src/mailroom_sandbox/job/vllm_metrics.py](src/mailroom_sandbox/job/vllm_metrics.py); [reports/serving/QWEN3-L4-LADDER-SUMMARY.md](reports/serving/QWEN3-L4-LADDER-SUMMARY.md)
- GPU dollars can be absent, derived from a short timestamp span, or derived from a fleet window that the ladder summary says under-counts Modal billing. ### Inferences
- The smallest check that separates a warm process from a usable document engine is a request that is long enough to cross the KV admission rule, with the response's model id and usage compared to the run lock, plus one mid-run `/metrics` scrape while more than one request is in flight. None of the default deploy, health, or `--check` steps do that.
- Production slice gates (`sandbox run gate`: quality, wrong archives, review rate, crashes) score extraction after the fact. They do not score the serving deploy. On the current production YAMLs there is no vLLM deploy to score.

### Gaps
- No golden "good deploy" fixture (expected argv, expected VRAM, expected TTFT on a fixed prompt) is wired into `serve()` or `sandbox health` in the files read here.
- Whether `sandbox health` follows redirects, checks the served model id against `default_model`, or only checks HTTP status, was not read in `health.py` during this pass. The README's claim that was used is the bearer check on `/v1/models` and the statement that `/health` 200 means the process is up.
