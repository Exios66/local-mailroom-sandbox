## Which of those are loaded on the production experiment path?

### Takeaway

All eight pipeline hotfixes are installation candidates at `runtime.activate`, which both local `sandbox run start` and the Modal job worker call through `runner.run_job`. Run YAML does not select them. Production slice specs under `config/runs/production/` are `task: pipeline` on `profile: openrouter`; the `*-modal-host` twins set `job.mode: modal`, so `deploy/modal_job.py` executes them on `sandbox-job` while the engine stays OpenRouter. Modal vLLM specialist specs such as SAND-032 use `profile: modal-vllm` and `job.mode: endpoint`, so the same `apply_hotfixes()` runs in the local runner and `deploy/modal_vllm.py` only serves the model. HF-005’s wrapper runs only if something calls `pipeline.watcher._DispatchPool.submit`. The job package does not reference that symbol.

### Inferences

- On a production `*-modal-host` slice, the process that loads HF-001–HF-008 is the `sandbox-job` worker, not the vLLM server. The documents are scored by an OpenRouter engine, so GPU quantization and context length on `sandbox-vllm` are not the serving path of those specs.
- On a Modal vLLM specialist or pipeline run launched as `--job-mode endpoint`, the same `apply_hotfixes()` runs locally. HF-006 and, for chunked extraction, HF-008 wrap specialist functions. HF-001 changes a result only for corporate records with a subtype. HF-002, HF-003, and HF-007 wrap judge and intake functions; an isolated specialist task does not, by itself, document those nodes. That last sentence is an inference from the targets and the task name, not a line-by-line trace of the specialist evaluator.
- HF-007 and HF-008 are wired in code and required by `_hotfix_check` (they are not given HF-005’s unavailable exception). They are omitted from the campaign contract’s required-patch table. That is a documentation gap, not an unwired hotfix.
- Run YAML never turns an individual hotfix on or off. A stale required hotfix fails preflight, so a new production lock is not written while that status holds. A worker whose `describe()` blob or check result differs from an already written lock fails at `verify_locked_hotfixes` even though activation itself only logs a miss.
- HF-005 can be `applied` on the worker image (the image installs `watchdog` and bundles `mailroom_sandbox`) and still not execute during an in-process `task: pipeline` job, because the job package does not call `_DispatchPool.submit`.

## What provenance must a remote Modal job bundle so hotfix identity matches the local checkout?

### Takeaway

The worker must carry the same `vendor_hotfixes.py` bytes, the same vendored target sources those fingerprints were hashed from, and the same scoring-hotfix module plus `subclass_corrections.jsonl`. At start, `verify_locked_hotfixes` requires `lock["vendor_hotfixes"] == vendor_hotfixes.describe()` and a passing `_hotfix_check`, and the same for `scoring_hotfixes`. `dependency_sources.verify_locked` separately refuses a dojo or pipeline source identity that differs from the lock. Default image bundling is the tracked `vendor/` trees plus the sandbox package. Cached or installed snapshot selection is extra image content, not a substitute for the hotfix file.

### Cited Findings

- Lock fields written at preflight that name code identity: `dependency_sources` from `dependency_sources.describe()`, `vendor_hotfixes` from `vendor_hotfixes.describe()` (`module_sha256` plus each fix’s id, target, and `source_sha256`), `scoring_hotfixes` from `scoring_hotfixes.describe()` (`module_sha256`, layer, and each target fingerprint), plus `git`, `package`, `spec_hash`, and `dataset`. — [preflight.py](../../../src/mailroom_sandbox/job/preflight.py) lock dict; [vendor_hotfixes.py](../../../src/mailroom_sandbox/vendor_hotfixes.py) `describe`; [scoring_hotfixes.py](../../../src/mailroom_sandbox/scoring_hotfixes.py) `describe`
- On this checkout those module hashes are `c9d3ab83a88534118bf3834900201c2ee03322aa7187f0e95060a77086d120cb` (pipeline hotfixes) and `54540a2f2df3a2ebd93609477a9d934d01427139e6412c429e11635f6ac76550` (scoring hotfixes), computed as sha256 of the file bytes, which is what both `module_sha256` functions do.
- Worker image contents that make those hashes and target fingerprints resolvable: `add_local_python_source("mailroom_sandbox")`; `vendor/llm-mailroom/src`; `vendor/llm-dojo-scoring/src`; `config/`; `data/fixtures/`; `data/labels/review/subclass_corrections.jsonl`. `SANDBOX_ROOT=/root` is what `repo_root()` / `vendor_dir()` use inside the container. — [modal_job.py](../../../deploy/modal_job.py)
- `verify_locked_hotfixes` compares the lock blob to `describe()` by equality, then runs `_hotfix_check` / `_scoring_hotfix_check`. A mismatch raises: “this process carries hotfix code other than the locked set (redeploy the job worker from the locking checkout, or re-lock with --force)” or “a locked hotfix is not in effect here.” Locks that omit the key are skipped. A started checkpoint missing either key is refused earlier in `run_job`. — [runner.py](../../../src/mailroom_sandbox/job/runner.py)
- `verify_locked` refuses when `lock["dependency_sources"]` differs from the current `describe()` for `dojo` or `pipeline`. A missing `dependency_sources` key returns without comparison (historical locks). `describe()` records `source`, `version`, `commit`, and `tree_sha256` (and `artifact_sha256` for a cached snapshot). — [dependency_sources.py](../../../src/mailroom_sandbox/dependency_sources.py) `describe`, `verify_locked`
- `bundle_job_snapshots` copies a selected `cached` snapshot directory, or an `installed` distribution plus its dist-info, and sets `SANDBOX_*_SNAPSHOT` or `SANDBOX_INSTALLED_*_ROOT`. It continues past components whose `current()` source is not `cached` or `installed`. The modal_job comment says default deployments still carry only the tracked vendor trees. — [dependency_sources.py](../../../src/mailroom_sandbox/dependency_sources.py) `bundle_job_snapshots`; [modal_job.py](../../../deploy/modal_job.py)
- The worker reads `spec.lock.json` and `dataset.jsonl` from the `sandbox-runs` volume and verifies the dataset sha256 before scoring. It does not re-download the dataset. `run_job` passes the store into `run_local_job`, which is where hotfix verification runs. OpenRouter-using locks fail before documents if `OPENROUTER_API_KEY` was not in the deploy secret. — [modal_job.py](../../../deploy/modal_job.py) module docstring and `run_job`
- Campaign contract: “Redeploy a Modal job worker when its bundled source or hotfix identities differ.” “A newer version number alone never proves a fix is incorporated.” “Existing locks cannot silently inherit a new patch generation.” — [EXPERIMENT-CAMPAIGN-CONTRACT.md](../../EXPERIMENT-CAMPAIGN-CONTRACT.md); [campaign-preparation-regressions.md](../../campaign-preparation-regressions.md) “Review and retirement”
- Guide: the process that executes the run re-checks at run start and refuses a hotfix set other than the lock’s, or a hotfix that is not in effect, so a worker deployed from older code never runs a locked job. — [vendor-hotfixes.md](../../vendor-hotfixes.md)
- AGENTS.md: for remote Modal jobs, bundle the same selected snapshots and installed family sources (with distribution metadata) when deploying the job worker; require matching provenance before accepting results. Never substitute latest stable for an experiment’s frozen commit. — [AGENTS.md](../../../AGENTS.md) “Dependency source selection”
- `describe()` for pipeline hotfixes does not include status. A worker can match the lock’s id list and fingerprints and still fail `_hotfix_check` if a target will not import or has gone stale. HF-005 `unavailable` is the only pipeline status that check allows through. Scoring checks fail on both `stale` and `unavailable`. — [preflight.py](../../../src/mailroom_sandbox/job/preflight.py) `_hotfix_check`, `_scoring_hotfix_check`

### Inferences

- Matching provenance for a remote job is four identities together: `vendor_hotfixes.module_sha256` plus the eight target fingerprints, `scoring_hotfixes.module_sha256` plus SHF target fingerprints including the corrections file, `dependency_sources` tree hashes for the pipeline and dojo layers the process actually imports, and the dataset sha256 already in the lock. Shipping only `vendor/` without `mailroom_sandbox` would omit the wrappers. Shipping a newer `vendor_hotfixes.py` against an old lock fails `describe()` equality even if the vendored targets still match.
- Because `module_sha256` is the whole file, a comment-only edit to `vendor_hotfixes.py` changes the lock identity and requires a new lock or a worker redeployed from that same file. It does not by itself change a target fingerprint.
- Endpoint-mode Modal vLLM experiments do not need this worker bundle for hotfix application. They need the local process that calls `activate()` to be the same checkout that wrote the lock. The vLLM image does not carry `vendor_hotfixes.py`.

### Gaps

- `git_snapshot()` and `package` field shapes were not quoted. They are on the lock, but their exact keys were not read.
- Whether this worktree’s selected dependency source is `vendored`, `cached`, or `installed` was not computed (`dependency_sources.describe()` was not executed). The bundle function’s branch depends on that selection.
- No deployed `sandbox-job` image digest was read, so “the worker that would run a production slice today” was not compared with `fedda378`.
