# Record the Qwen 3.5 boot first

The single most valuable measurement is the **boot outcome of `Qwen/Qwen3.5-9B` at one named `max_model_len` on one L4**: the vLLM process either reaches ready or raises at engine init, and cold-boot seconds are the measured time until ready. That result decides whether this checkout's default context of **16384** is a length the GPU can hold, and whether a second boot at **32768** is allowed to proceed. It is worth taking on that checkpoint, served **text-only with online fp8** by the GPU app **`sandbox-vllm`**, when the process that will later score documents has the repaired pipeline wrappers **HF-001 through HF-008** and the scoring wrappers **SHF-001 through SHF-013** in effect. Those wrappers repair silent-wrong classification and extraction. They leave vLLM boot, context, quantization, and GPU container time untouched. The production `*-modal-host` slices run OpenRouter pipelines on the CPU worker **`sandbox-job`**, so they never collect this boot. On 2026-11-20 a read-only app list showed neither app. A design that records the boot sets **`job.max_wall_seconds` to 3600** and **`job.cost_cap_usd` to 2.00**. No paid run was started. The operator must supply initials.

A ready result at 16384 followed by a raise at 32768 keeps the default and leaves long contracts on the chunked specialist window. A ready result at 32768 is what lets a later run test a longer window. Cold-boot seconds belong in the same record, measured from container start until the server is ready. The planning constant of 120 seconds and the ladder's **216** second CUDA-graph boot are different postures on `Qwen/Qwen3-8B-AWQ`, and this tree has no cold-boot number for the 9B ([reports/serving/QWEN3-L4-LADDER-SUMMARY.md](../../../reports/serving/QWEN3-L4-LADDER-SUMMARY.md), [docs/RUN-COST-DERIVATION.md](../../RUN-COST-DERIVATION.md)). A useful boot log therefore names the `max_model_len`, the quantization, and the GPU, keeps the exception text on a raise, and records whether those kernels loaded. A port wait, a `/health` 200, and an app-list state of `deployed` all stop short of that record. `/health` means the process is up. ## Conclusion

Hotfix identity and a named boot answer different questions, and this tree already has a recorded case of scoring one model while the GPU served another. The OpenRouter slices can carry every repaired wrapper, pass `verify_locked_hotfixes`, and still never start `sandbox-vllm`. The account listing on 2026-11-20 had no serving app to scrape. The default code path will attempt `Qwen/Qwen3.5-9B` online fp8 at 16384 the first time that app is deployed, on an image whose Qwen3.5 boot is still open, and on a GPU whose 32768 behavior is documented for other weights.

That orders the next dollar. Capture raise-or-ready and the cold-boot seconds on the 9B, with the scoring process pinned to this hotfix generation, inside `job.max_wall_seconds` 3600 and `job.cost_cap_usd` 2.00, and with a person supplying initials. Use the same session for the concurrency cliff and a five-contract length-finish check only after the server is ready and the mid-run scrapes are on disk. If 16384 raises, the default deploy is blocked, and the checkpoints this tree already treats as boot-valid at a usable L4 context, `Qwen/Qwen3-8B-AWQ` and `ibm-granite/granite-4.2-8b-fp8` at 32768, are the serving choices a later quality comparison can use. That comparison is a separate experiment, at the sample size the production bars and the billed-total rule already name, and it waits on a boot log this checkout does not have.
