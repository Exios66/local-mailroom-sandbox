# Modal vLLM measurement priorities

Checked against this checkout on 2026-11-20. No paid or live work was run: no `sandbox run start`, no `modal deploy`, no `vllm probe`. Every dollar figure below is a number already written in a source, or a planning product of those numbers. It is not a new measurement and it is not a charge.

Model-id status for the proposed paid probe: `Qwen/Qwen3.5-9B` is the app default in this checkout (online fp8, text-only, L4). Mark it **provisional**. The models research may still be confirming the id. All live serving numbers cited here are `Qwen/Qwen3-8B` or `Qwen/Qwen3-8B-AWQ` on Modal L4, vLLM `v0.29.0`, unless a row says otherwise.

Ranking, by how much the next measurement would change a real deploy or model decision per GPU-dollar:

1. Boot outcome at a stated `max_model_len` on provisional `Qwen/Qwen3.5-9B` (raise vs ready, plus measured cold-boot seconds). One boot can forbid 32768 on L4 or allow long-document serving.
2. Concurrency cliff on that same boot: client concurrency against `max_num_seqs`, preemptions, KV-cache percent, and per-replica request split. This was the largest serving lever on the 8B-AWQ program, and the 9B fp8 KV budget is unmeasured.
3. GPU container-time split (cold boot, busy window, idle/scaledown, replica count), stored so a later 1,000-document billed comparison is possible. Do not rank arms as cheaper from this probe.
4. Length-finish count, chunk count, skipped chunks, and schema-valid rate on a handful of contracts, only after the boot and the short-document sweep have been recorded. This is the historical long-document cost mode.
5. Prefix-cache hit rate, captured in the same `/metrics` scrape as the cliff. It is pinned on and has no committed hit rate that changed a decision. Do not spend a separate run for it.
6. Wrong-but-confident classification and empty or hollow extraction. Existing per-run figures already answer the classification question when items carry class probability. They do not change `max_model_len`, concurrency, or the GPU. Score them if the items exist. Do not buy GPU time to rediscover them.

## Which deploy decisions do existing figures already answer, and which have no figure because the measurement is missing?

### Takeaway

House figures answer where a document went, whether class probability ranks right answers above wrong ones, subclass accuracy, per-document latency, and whether a decision-model sorter is non-inferior to an LLM sorter. They do not answer boot success, the concurrency cliff, prefix-cache hit rate, scaledown share, length-finish waste, or chunk loss. Those deploy decisions have designs and, for Qwen3-8B-AWQ, some live tables, but no house figure, and no committed vLLM `/metrics` text.

### Inferences

- A deploy decision already has a figure only when it is “where did documents go,” “does probability rank errors,” “how does latency grow with size on this run,” or “is the decision-model sorter non-inferior on the H5 margins.” Engine knobs do not.
- The next figure worth adding is not another quality forest plot. It is a serving figure whose inputs do not exist as committed scrapes: boot result, container-time split, and the concurrency cliff. Until those series are saved, a house figure cannot be drawn, and the 8B program figures must not be copied onto 9B.
- Item `usage.cost` in a latency subtitle can be quoted as if it were a Modal charge. The cost-claim rule does not automatically attach to that subtitle. Any new serving figure has to label the basis in the subtitle the way `cost-quality` already does.

### Gaps

- This pass did not inventory every SVG under `reports/`. The catalog and the ladder summary are the figure lists that were read. A campaign tree may contain extra latency SVGs from older report builds that only wrote `latency.svg`.
- No committed numeric prefix-cache hit rate was found. The code path exists. Whether any uncommitted run store has a scrape was not checked. `data/runtime/` is gitignored.

## Which failure modes dominate cost or quality, and what are the limits of that evidence?

### Takeaway

On the live Qwen3-8B-AWQ Modal program, long-document decode (contracts and mergers), not cold start, dominated GPU time once the fleet was warm, and a bad admission setting made a short-document run 3.8 times slower than the admission-32 run at the same sequence cap and concurrency (149.4 s versus 39.0 s). The 3.2 times figure compares 149.4 s with an earlier 46.1 s run that also changed sequence cap and concurrency. Structured-output length finishes were a real decode-cost mode on contracts and mergers. The insurance schema-invalid rate was a harness bug, not a vLLM failure. Wrong-but-confident classification and empty extraction are documented on other runs, including an OpenRouter pipeline audit whose raw items are not in this checkout. None of these rates have been measured on provisional `Qwen/Qwen3.5-9B`.

### Cited Findings

Planning advice adds a 120 s cold start and a scaledown that is never under 600 s. The attended specialist default is `scaledown_seconds` 120, and unattended or overnight is 600. Default `min_containers` is 0, so the app scales to zero. — [RUN-COST-DERIVATION.md](../../docs/RUN-COST-DERIVATION.md); [QWEN3-L4-LADDER-SUMMARY.md](../../reports/serving/QWEN3-L4-LADDER-SUMMARY.md); [SAND42 experiment design](../../docs/SAND42-EXPERIMENT-DESIGN.md); [deploy/modal_vllm.py](../../deploy/modal_vllm.py); [experiments.md](../../docs/experiments.md)

At n=50 the same defect is described as about one wave, 8–15%. - `max_model_len` boot failure is a documented vLLM v0.29.0 behavior, not a measured 9B event. The deploy readme says v0.29.0 raises at boot when the KV pool cannot hold one request at the cap. - The concurrency cliff is measured on Qwen3-8B-AWQ, live Modal L4. ### Inferences

- Cold start and scaledown change the cap and the idle bill. They do not explain why a warm merger cell costs orders of magnitude more wall than a warm correspondence cell. The first paid minute on 9B should still record the boot, because a raise at 32768 changes the deployment before any quality number matters, and because 9B online fp8 has no boot measurement in this tree.
- The concurrency cliff and length-finish loops are the two modes that have already changed a runbook on 8B (max_inputs equals max_num_seqs; temperature 0.7 and do not raise the cap). Both can move on a different weight, quantization, and KV layout. They are the modes a 9B probe can falsify cheaply.
- Prefix-cache hit rate, wrong-but-confident class calls, and empty extraction should be columns on that probe. They should not be the reason the probe exists. Insurance schema failure should not be re-bought as an engine experiment. The RCA says the schema contract was the cause.
- Any sentence of the form “API is 18 times cheaper than Modal” or “L5 cut dollars per document 43%” is a historical calculation on small n using container-time estimates and, on the API side, list price times tokens. Under the current figure rule those sentences are not cost decisions.

### Gaps

- No live `Qwen/Qwen3.5-9B` boot time, cliff, hit rate, length-finish count, or extraction score was found in the reports read.
- Provider-billed per-run totals from the Modal usage page were not in the repo. The ladder says to reconcile there because the ledger under-counts. That reconciliation was not redone on 2026-11-20, and this research did not open the usage page.
- The L4 rate used in the derivation is $0.80 per hour. The Modal skill says that rate was checked against modal.com/pricing on 2026-09-09. It was not re-checked for this note. A planning cap that multiplies $0.80 can be stale.
- SAND-40 and SAND-42 numeric claims are taken from the design and summary documents. The underlying `items.jsonl` stores are not committed, so those counts were not re-summed from raw rows.

## What minimal measurement set distinguishes those modes, and how may cost be stated?

### Takeaway

Eight measurements, all collectable on one boot, separate a boot failure, a concurrency cliff, an idle scaledown, a prefix-cache miss, a decode loop, a dropped chunk, and a confident wrong class. Cost is GPU container-time. List price times tokens is not a charge. No arm is cheaper unless both arms have provider-billed totals and at least 1,000 paired documents. The only pre-registered margins to carry onto a card are the ones already written: quality delta lower bound above −0.02 for a serving change, H5’s 2-point and 4-point margins on their own comparison, and the production slice bars, which are diagnostic below n=500.

### Cited Findings

- Modal bills occupied container time. The derivation writes `cost_modal` from the sum of `latency_s / concurrency` plus cold boot, times the L4 hourly rate over 3600. A later section replaces that with `billed_seconds` from the telemetry window times replicas times the hourly rate over 3600. Replicas bill the full wall on every replica. A route fleet bills the sum across apps. `min_containers=1` also bills idle from deploy to teardown. An unrecorded window sets `measured: false` and must not invent a number. — [RUN-COST-DERIVATION.md](../../docs/RUN-COST-DERIVATION.md)
- List price times tokens is the OpenRouter estimate (`per_1k_docs_usd`). A billed total is `provider_reported_usd`, used only when it covers every compared document. `COST_CLAIM_MIN_DOCS` is 1000. — [experiment figures](../../docs/experiment-figures.md); [sorter_arms.py](../../src/mailroom_sandbox/sorter_arms.py)
- Runner cost caps are estimates of GPU time, not invoice limits. Image builds, CPU prewarm, cold boot, scaledown, extra replicas, and in-flight calls can add charges the cap does not see. The GPU cap does not limit OpenRouter. `api_cost_cap_usd` does, and this probe should not send any agent to OpenRouter. — [experiments.md](../../docs/experiments.md)
- `gate.json` records the production slice comparison (quality, wrong-archive rate, review rate, crashes, judge errors) against `config/production/bars.yaml`. Engine series belong in the vLLM scrape and the run directory, not in `gate.json`, unless the gate is extended. The bars are quality 0.90, wrong-archive max 0.02, review max 0.05, `per_class_from_n` 500, `min_scorable_per_class` 20. — [bars.yaml](../../config/production/bars.yaml); [gate_render.py](../../src/mailroom_sandbox/job/gate_render.py)
