# Critical regressions — always guard against these

Every PR checks its diff against this list. Each entry is a failure this repository
has already shipped or nearly shipped. The common thread: **the run finishes and the
number looks plausible, but it is wrong.** A crash is cheap; a silent wrong score,
draw, model or cost is not. If a change touches the named area, the PR's Critical
regressions section says which guard covers it (test, preflight check, or audit), or why
it does not apply.

Campaign reviews also use the stable `CP-*` entries in the
[campaign preparation checklist](campaign-preparation-regressions.md), which links
patch state, tests and open acceptance to the master tracking discussion.

## How to use this list in a PR

1. Name the rows your change touches in the PR's **Critical regressions** section.
2. For each, cite the guard that covers it (test node, preflight check, audit command)
   and the command output from this head, or explain why the row does not apply.
3. A change that weakens or removes a guard needs an explicit reviewer sign-off in
   the PR and an entry under **Risks / follow-ups**.
4. A new failure class found in review or in a run gets a row here in the same PR as its fix.
