# Campaign reports

Every report and analysis of a campaign run is generated from that run's logs and filed
here, one tree per campaign. Start at a campaign's `README.md` and click down to any run's
exact records. This file is hand-written; everything below `<campaign>/` is generated by
`sandbox report build` (`src/mailroom_sandbox/report_campaigns.py`) and must not be edited
by hand.

| campaign | full name | index |
| --- | --- | --- |
| `rb1` | runbook-v1: the evaluation runbook, phases 0-9, rows R00..R90 | [rb1/README.md](rb1/README.md) |

## Naming grammar

All names are lowercase and hyphen-separated, so plain `grep` and `find` isolate a
campaign, an experiment, a run or one iteration without `-i`.

| piece | form | example |
| --- | --- | --- |
| campaign ID | `[a-z][a-z0-9]*` | `rb1` |
| row | the runbook CSV row ID, lowercased | `r01`, `g0`, `g6b` |
| experiment key | `<campaign>-<row>` | `rb1-r01` |
| experiment folder | `<key>-<slug>` (slug from `config/campaigns/<campaign>.yaml`) | `rb1-r01-provider-pin-smoke` |
| run_id | `<key>-<rest>`, at most 64 characters, never ending in `-iNN` | `rb1-r01-smoke-qwen3.7-flash` |
| iteration | `iNN`, from `i01` | `i01` |
| run artifact | `<run_id>-<iNN>.<name>.<ext>` | `rb1-r03-sorter-v0-dev-i01.report.md` |
| experiment artifact | `<key>.<name>.<ext>` | `rb1-r02.sheet.csv`, `rb1-g0.checkpoint-gate.json` |

Only `README.md` (one per folder, for navigation) and the campaign's `index.jsonl` are
exempt from the prefix rule. A committed run config is `config/runs/<run_id>.yaml`, its
`run_id` equals the file stem, and the run_id always starts with its experiment key; the
served-provider ledger of a launch goes to `data/runtime/<key>/served-<model>.jsonl`.
`tests/test_report_campaigns.py` checks every committed `config/runs/rb1-*.yaml` against
the grammar. In code: `parse_run_id`, `format_run_id`, `parse_artifact`, `format_artifact`,
`parse_iteration` and `format_iteration`.

Some searches:

```bash
find reports/campaigns -name 'rb1-r03*'                # every R03 record
find reports/campaigns -name 'rb1-r03-sorter-v0-dev-i02.*'   # one iteration
grep '"experiment": "rb1-r01"' reports/campaigns/rb1/index.jsonl
```

## Layout

```text
reports/campaigns/<campaign>/
  README.md                   experiments by phase, status, links
  index.jsonl                 one row per run iteration: campaign, experiment, run_id,
                              iteration, path, status, spec_hash, started, finished
  <key>-<slug>/
    README.md                 purpose, configs, runs with headline results, gate files
    <key>.<name>.<ext>        experiment-level records (R02 sheet, G0 digest, comparisons)
    <run_id>/<iNN>/
      README.md               how to read the run: config, spec hash, generation,
                              dependency_sources, git, launches, where everything is
      <stem>.manifest.json    files the builder owns, with sha256
      logs/                   spec lock, checkpoint, events (copied when small),
                              node and served-ledger digests, spend authorization digest
      traces/                 items.jsonl (size-capped) and path + sha256 references to
                              large raw data: dataset, nodes, span mirror, trace packs
      outputs/                predictions.csv, item-scores.csv
      report/                 report.md, report.json
      analysis/               metrics.json (run scorer + serving renderer), stats.json,
                              confusion.csv when items carry their own truth
      figures/                latency.svg, per-class-f1.svg
      docs/                   config copy, spec core, prompt lock, caveats.md, and gate
                              results such as <stem>.r01-gate.json
```

`<stem>` is `<run_id>-<iNN>`.

**Iterations.** An iteration is one locked generation of a run_id: each `archive-*`
directory a forced re-lock (`preflight --force`) moved aside, oldest first, then the live
store. Relaunches and resumes inside one generation append to the same items, so the run
README lists them as launches of that iteration instead of new iterations.

**What the numbers are.** Headline scores come from the run's own record in
`reports/experiment_log.jsonl`, matched to the locked generation with
`mailroom_sandbox.job.evidence.record_matches`; when no record matches, the report says
"not recorded" and shows nothing. Cost and latency come from
`mailroom_sandbox.job.metrics.serving_record_from_store`, with its `cost_basis` stated.
Nothing is rescored. Mock and replay runs carry a banner and are never evidence.
`docs/<stem>.caveats.md` lists every limitation the builder detected.

**Large data.** Files over the copy cap (256 KiB, `--max-copy-bytes`), datasets, span
mirrors and trace packs are referenced by path and sha256, never copied. Paths are logical
(`data/runtime/runs/<run_id>/...`) so the tree is machine-independent. Commit READMEs,
reports, digests and small CSVs; leave large traces in `data/`.

## Commands

```bash
sandbox report build --run <run_id> [--iteration N]   # one run (every iteration by default)
sandbox report build --campaign rb1                   # campaign + experiment READMEs, index.jsonl
sandbox report build --campaign rb1 --check           # exit 1 when committed indexes are stale
sandbox report build --run <run_id> --runs-dir <dir>  # read stores elsewhere, read-only
```

`--check` writes nothing and exits 1 when any generated file differs. The builder never
writes into a run store and never deletes a file it does not own (gate outputs in `docs/`
stay). Run reports are also built automatically at the end of every non-mock run whose
run_id is in the grammar (`maybe_build_campaign_reports` in `job/runner.py`); a failure
there logs a warning and never changes the run's result. `SANDBOX_CAMPAIGN_REPORTS=0`
turns the hook off and `SANDBOX_CAMPAIGN_REPORTS_DIR` moves the tree (tests).

Gate scripts write into the tree too: `python scripts/check_g0.py --write-digest` files
`rb1-g0.checkpoint-gate.{json,md}` under `rb1/rb1-g0-checkpoint/`, and
`python scripts/check_r01_smoke.py ... --write-docs` files `docs/<stem>.r01-gate.json` in
each smoke run's iteration. Both refresh the campaign indexes.

## Writing into the tree from a script

Analysis scripts (for example the sorter-vs-decision comparison) use the paths API instead
of building paths by hand:

```python
from mailroom_sandbox.report_campaigns import campaign_paths, experiment_paths

run = campaign_paths("rb1-r13-decision-arm-a")   # latest iteration in the store, i01 without one
run.mkdirs()
run.file("analysis", "mcnemar", "json")          # .../i01/analysis/rb1-r13-decision-arm-a-i01.mcnemar.json
run.figures                                      # also .logs .traces .outputs .report .analysis .docs

exp = experiment_paths("rb1-r13")                # experiment folder, for cross-run comparisons
exp.file("sorter-vs-decision", "csv", "analysis")  # .../rb1-r13-decision-routing/analysis/rb1-r13.sorter-vs-decision.csv
```

Files written this way are not owned by the builder, so a rebuild keeps them; run
`sandbox report build --campaign rb1` afterwards to refresh the indexes.
